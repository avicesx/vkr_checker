# Правила нормоконтроля (`rule_engine`)

Пакет проверяет оформление документа по декларативному набору правил и
возвращает отчет с адресом нарушения, ожидаемым и фактическим значением.
Разбор DOCX остается за `parser.docx`: правила читают готовый
`ParsedDocxDocument`, где каскад стилей уже разрешен, а единицы приведены к
пунктам и миллиметрам.

Набор покрывает девять проверок ВКР: текст, поля страницы, иерархию и нумерацию
заголовков, оформление заголовков, состав разделов и оглавление. Для вузовских
методичек добавлены геометрические проверки (`page_number_position`,
`page_format`) и межстрочный интервал (`line_spacing`): готовые профили
`mpgu`, `urgpu` и `urfu` лежат в `rule_engine/rules/` и загружаются по id вуза
(см. [раздел 9](#9-профили-вузов)).

| Вид правила | Что проверяет | Объект | `scope` |
|---|---|---|---|
| `font` | гарнитура, кегль, начертание | ран (фрагмент текста) внутри абзаца | абзацы, `headings` |
| `indent` | отступ первой строки, слева, справа | абзац | абзацы, `headings` |
| `margin` | левое, правое, верхнее, нижнее поле, корешковый отступ | секция | `sections` |
| `heading_levels` | стартовый уровень, перескоки уровней, максимальная глубина | заголовок из `document_tree` | `headings` |
| `heading_numbering` | последовательность номеров, номер родителя, глубина номера, точка после номера | заголовок с `section_number` | `headings` |
| `heading_format` | точка в конце заголовка, регистр, выравнивание | заголовок и его абзац | `headings` |
| `required_sections` | наличие разделов и порядок их следования | структура документа | `document_structure` |
| `toc` | наличие оглавления, записи, сверка с заголовками | `TocContainerBlock` | `toc` |
| `page_number_position` | колонтитул с номером страницы и выравнивание номера | абзац колонтитула | `headers_footers` |
| `page_format` | ширина и высота листа, допуск, ориентация | секция | `sections` |
| `line_spacing` | множитель межстрочного интервала | абзац | абзацы, `headings` |

## 1. Быстрый старт

```python
from parser.docx.pipeline import DocxParserPipeline
from rule_engine import DEFAULT_RULESET_PATH, RuleEngine, load_ruleset

document = DocxParserPipeline("vkr.docx").parse()
engine = RuleEngine(load_ruleset(DEFAULT_RULESET_PATH))
report = engine.check(document)

print(report.passed, report.summary.violations_total)
for violation in report.violations[:5]:
    print(violation.rule_id, violation.found_text, violation.location.block_id)
```

Документ, уже сохраненный в JSON парсера, проверяется без повторного разбора:

```python
report = RuleEngine(load_ruleset("rules.json")).check_json_file("vkr.json")
```

Готовый профиль вуза подключается по идентификатору:

```python
from rule_engine.rules import load_profile_ruleset

engine = RuleEngine(load_profile_ruleset("urfu"))
report = engine.check(document)
```

Ручной прогон с печатью сводки и выгрузкой `{имя}_rules.json`:

```bash
python manual_test/check_rules.py manual_test/test.docx \
    --rules rule_engine/rules/vkr_test_rules.json \
    --outdir manual_test/out
```

Флаги CLI: `--rules` (набор правил), `--pdf` (эталонный PDF, иначе ищется
одноименный рядом с `.docx`), `--outdir`/`--out` (куда писать отчет), `--limit`
(сколько нарушений печатать, по умолчанию 10).

## 2. Формат набора правил

Набор — один JSON-файл. Неизвестные ключи запрещены (`extra="forbid"`), поэтому
опечатка в имени поля падает на загрузке, а не молча игнорируется.

```json
{
  "ruleset_id": "vkr-rule-engine-test",
  "ruleset_version": "2.0.0",
  "description": "Тестовый набор",
  "rules": [
    {
      "rule_id": "font_body_text",
      "kind": "font",
      "severity": "error",
      "message": "Основной текст набирается гарнитурой Times New Roman, 14 pt",
      "requirement_ref": "Методические указания, п. 4.2",
      "target": {"scope": "body_text"},
      "expected": {"family": "Times New Roman", "size_pt": 14.0}
    }
  ]
}
```

Общие поля правила:

| Поле | Обязательно | Смысл |
|---|---|---|
| `rule_id` | да | уникальный идентификатор внутри набора |
| `kind` | да | `font`, `indent`, `margin`, `heading_levels`, `heading_numbering`, `heading_format`, `required_sections`, `toc`, `page_number_position`, `page_format`, `line_spacing` |
| `message` | да | формулировка требования для отчета |
| `severity` | нет | `error` (по умолчанию), `warning`, `info` |
| `requirement_ref` | нет | ссылка на пункт методических указаний |
| `target` | нет | область действия, по умолчанию `{"scope": "body_text"}` |
| `expected` | да | ожидаемые значения, зависят от `kind` |

`rule_id` в пределах набора уникальны; `ruleset_id` и `ruleset_version`
попадают в отчет, поэтому по ним видно, чем именно проверяли документ.

### Области действия (`target.scope`)

| `scope` | Что попадает в выборку |
|---|---|
| `body_text` | абзацы верхнего уровня `w:body` без заголовков, подписей и списков, а также без блоков исключенных контекстов (по умолчанию) |
| `body_paragraphs` | все абзацы верхнего уровня `w:body` как есть, кроме блоков исключенных контекстов |
| `all_paragraphs` | тело, ячейки таблиц, колонтитулы и сноски |
| `table_cells` | только абзацы внутри ячеек таблиц |
| `headers_footers` | только колонтитулы всех секций (в них живет номер страницы) |
| `footnotes` | только сноски и концевые сноски |
| `sections` | секции целиком: поля страницы и формат листа (`margin`, `page_format`) |
| `headings` | заголовки в порядке следования из `document_tree` (уровни, нумерация, оформление) |
| `document_structure` | структура документа: состав и порядок разделов |
| `toc` | блоки оглавления `TocContainerBlock` и их записи |

Строки оглавления (`TocContainerBlock.raw_paragraphs`) в выборку не попадают
никогда: это навигация, а не текст работы. Правило `margin` обязано иметь
`scope="sections"`, `page_format` — тоже `sections`, `page_number_position` —
`headers_footers`, правила `font`, `indent` и `line_spacing` — любую из абзацных
областей или `headings`, а структурные правила (`heading_*`,
`required_sections`, `toc`) работают только в своей области: `headings`,
`document_structure` и `toc` соответственно. Несовместимый `scope` — ошибка
загрузки набора, а не молчаливое нарушение.

Исключения по умолчанию действуют только для `body_text` — это семантическая
выборка «основного текста». Остальные области берут объекты как есть: правило
«все ячейки таблиц» не должно пропускать элементы списков внутри ячеек.

### Контекст блока (`target.exclude_contexts`)

Титульный лист, сервисные листы и листинги кода оформляются по требованиям
методички к служебным страницам и коду, а не к основному тексту: реквизиты вуза
набраны 10–12 pt, лист задания — 12 pt без красной строки, а листинги —
моноширинной гарнитурой. Проверять их правилами «основной текст» значит получать
сотни нарушений там, где оформление соответствует другому разделу методички.

Каждый блок документа получает один из трех контекстов:

| Контекст | Что это |
|---|---|
| `title_page` | строки титульного листа и сервисных листов: реквизиты вуза, тема, подписные строки (`М.П.`, «Подпись»), строки листа задания, календарного плана, акта внедрения/приемки, аннотации, реферата, отзыва; мелкий кегль, центрирование, город и год |
| `code_listing` | листинги: моноширинная гарнитура (Courier New, Consolas, …) или строки с код-синтаксисом; смежные листинги сливаются в один регион |
| `body` | всё остальное; заголовки и подписи рисунков/таблиц всегда `body` — у них свои правила |

Сервисная зона — это зона, а не номер страницы. Титул открыт от начала документа
и закрывается первым структурным заголовком, блоком оглавления или началом
основного текста; две страницы лимитом не являются, потому что лист задания или
акт внедрения занимает несколько листов. Сам сервисный лист распознается по
заголовку («ЗАДАНИЕ», «КАЛЕНДАРНЫЙ ПЛАН», «АКТ ВНЕДРЕНИЯ», «РЕФЕРАТ», …) в любом
месте документа. Внутри зоны реквизит — строка без завершающей точки («Екатеринбург»,
«2026», «(фамилия, имя, отчество)», «Нормоконтролер: …») — получает контекст
`title_page`; длинное предложение с точкой возвращает зону в основной текст.

Титульная зона требует доказательства: хотя бы одну строку с реквизитом вуза или
подписью (`TITLE_REQUIRED_SIGNALS = {"marker"}`). Без такого маркера короткая
строка без точки остается `body` — иначе фильтр скрывал бы настоящие нарушения
шрифта и отступа. Строка, состоящая только из подписного реквизита («(подпись)»),
распознается как `title_page` в любом месте документа: абзацем текста она не
бывает.

Классификация детерминированная: `rule_engine.context` использует только поля
`ParagraphBlock` (выравнивание, раны, текст, кегль), позицию блока в документе и
`cross_ref_index` для подписей. Нет моделей, обращений к сети, времени и
случайности, поэтому один и тот же документ всегда дает один и тот же набор
контекстов и одинаковый отчет. Сомнительный блок остается `body`: показать
лишнее нарушение дешевле, чем скрыть настоящее.

Поле `target.exclude_contexts` — список контекстов, которые правило не проверяет:

* по умолчанию `["title_page", "code_listing"]` — «основной текст» работает на
  документе с титулом и листингами сразу: перечислять StyleId не нужно;
* `[]` отключает фильтр: проверяются все абзацы области, включая титул и
  листинги (прежнее поведение);
* элементы списка — строки контекстов; неизвестное имя ничего не фильтрует, а
  строка или число вместо списка отвергаются загрузкой набора с ошибкой
  `exclude_contexts: Input should be a valid list`.

Фильтр действует только для абзацных областей основного текста (`body_text` и
`body_paragraphs`). Заголовки (`headings`), оглавление (`toc`), ячейки таблиц,
колонтитулы, сноски, `all_paragraphs` и `document_structure` берут объекты как
есть: у заголовков, оглавления и структуры свои правила, и контекстный фильтр не
должен скрывать от них блоки. Счетчики `objects_checked` в отчете считают только
блоки, прошедшие фильтр.

Набор, написанный до появления поля (например,
`rule_engine/rules/vkr_test_rules.json`), обратно совместим: поле
необязательное, отсутствие равнозначно значению по умолчанию, поэтому поведение
на абзацах `body` не меняется. Новое поле можно не указывать и явно:
`"target": {"scope": "body_text"}`.

Пример: проверить шрифт и на титульном листе, но не в листингах (титул тоже
набран Times New Roman 14 pt, а код — моноширинный):

```json
{
  "rule_id": "font_without_listings",
  "kind": "font",
  "severity": "error",
  "message": "Весь текст, включая титульный лист, набран Times New Roman, 14 pt",
  "target": {
    "scope": "body_text",
    "exclude_contexts": ["code_listing"]
  },
  "expected": {"family": "Times New Roman", "size_pt": 14.0}
}
```

Полное отключение фильтра — пустой список, прежнее поведение правила:

```json
{"target": {"scope": "body_text", "exclude_contexts": []}}
```

Флаги расширяют выборку `body_text`:

| Поле `target` | По умолчанию | Что делает при `true` |
|---|---|---|
| `include_headings` | `false` | проверяет абзацы с `heading_info` |
| `include_captions` | `false` | проверяет подписи рисунков, таблиц и приложений |
| `include_list_items` | `false` | проверяет элементы списков (`list_info` или итоговый `num_id`) |
| `include_empty` | `false` | проверяет пустые абзацы и абзацы только с графикой/формулой |
| `style_ids` | `[]` | ограничивает выборку перечисленными `styleId` (`[]` — без ограничения; работает во всех областях) |
| `exclude_roles` | `[]` | не проверять заголовки этих ролей вместе с поддеревом (`appendix`, `task_sheet`, `title_page`); только для `headings` и `document_structure` |
| `exclude_contexts` | `["title_page", "code_listing"]` | не проверять блоки этих контекстов в областях `body_text` и `body_paragraphs` (`[]` — без фильтрации) |
| `min_heading_confidence` | `heuristic_visual` | минимальная уверенность распознавания заголовка: `explicit_outline_or_style`, `structural_keyword_match`, `heuristic_visual` |

Подписи определяются по `cross_ref_index` (`figures`, `tables`, `Apps`):
`caption_block_id` каждого объекта исключается из выборки.

## 3. Виды правил и `expected`

### `font` — шрифт рана

| Поле | По умолчанию | Смысл |
|---|---|---|
| `family` | `null` | гарнитура; сравнение по нормализованному имени (см. ниже) |
| `size_pt` | `null` | кегль в пунктах (1…200) |
| `bold` | `null` | ожидаемое начертание |
| `italic` | `null` | ожидаемое начертание |
| `size_tolerance_pt` | `0.5` | допуск по кеглю, пункты |
| `check_complex_script` | `false` | дополнительно сверять `font_cs` |
| `normalize_family` | `true` | сравнивать гарнитуру по нормализованному имени; `false` — прежнее строгое сравнение |

Проверяются эффективные свойства рана (`RunFontPropertiesEffective`), то есть
результат каскада «документ → стиль абзаца → стиль символа → прямое
форматирование». Пропускаются раны без видимого текста, раны внутри полей
(`in_field`) и скрытый текст (`vanish_hidden`).

Гарнитура сравнивается по нормализованному имени: регистр, пробелы, дефисы и
подчеркивания не важны, subset-префикс `XXXXXX+` и стилевые маркеры PostScript
(`-MT`, `-PS`, `-PSMT`, `-Bold`, `-Italic`, `-Regular`, `-Roman`) отбрасываются
как начертание, а не как часть имени. Поэтому `TimesNewRoman`,
`ABCDEF+TimesNewRoman-BoldMT` и `Times New Roman` — одна гарнитура; вариант
«Roman» в составе имени (`Times New Roman`) сохраняется. Отключить
нормализацию: `"normalize_family": false`.

Символические раны правило не проверяет: гарнитуры Symbol, SymbolMT, Wingdings,
Webdings и подобные, а также раны, весь видимый текст которых состоит из
небуквенноцифровых знаков (`±`, `≤`, `×`). Кегль и начертание у математических
знаков не осмысленны, поэтому такие раны не дают нарушений шрифта.

В `pdf_only` гарнитура сверяется так же, как в DOCX: запись шрифта PDF
(`TimesNewRoman`, `TimesNewRoman-BoldMT`, `ABCDEF+…`) сравнивается с ожидаемым
именем по нормализованному ключу, поэтому запись шрифта не дает шума. Настоящая
другая гарнитура (`LiberationSans`, `NimbusRomNo9L`, `CMR10`) — реальное
нарушение и ожидаемая находка: это неверное оформление, а не артефакт разбора.
Не сверяется только `font_cs` (complex script): в PDF он не измеряется. Кегль и
начертание проверяются всегда. Подробности — в разделе «Деградация по
возможностям разбора».


### `indent` — отступы абзаца

| Поле | По умолчанию | Смысл |
|---|---|---|
| `first_line_mm` | `null` | красная строка; отрицательное значение — висячий отступ |
| `left_mm` | `null` | отступ слева |
| `right_mm` | `null` | отступ справа |
| `tolerance_mm` | `0.5` | допуск, миллиметры |

В `pdf_only` правило не проверяет отступы и не создает нарушений. Измерение
есть — красная строка считается как сдвиг первой строки относительно второй, —
но как источник требования отступ ненадежен: у маркированных абзацев и списков
маркер сдвигает первую строку и дает ложные +20 мм и больше, а у разорванных
версткой абзацев сдвиг теряется (см. «Деградация по возможностям разбора»).

### `margin` — поля страницы

| Поле | По умолчанию | Смысл |
|---|---|---|
| `left_mm`, `right_mm`, `top_mm`, `bottom_mm` | `null` | поля страницы |
| `gutter_mm` | `null` | корешковый отступ |
| `tolerance_mm` | `1.0` | допуск, миллиметры |

Правило применяется к каждой секции отдельно: в отчет попадает нарушение на
секцию, а не одно на документ. Незаданные поля (`null`) не проверяются.
В `pdf_only` допуск расширяется до `max(tolerance_mm, 1.5)` мм: поля оценены
по геометрии текста, и отклонение 1.5 мм — погрешность оценки, а не нарушение.
Поле 13.7 мм при ожидаемых 15 мм (отклонение 1.3 мм) в `pdf_only` попадает в
допуск ±1.5 мм и нарушением не является; нарушением остается расхождение
больше допуска, например нижнее поле 26.5 мм при ожидаемых 20 мм.


### Деградация по возможностям разбора (`capabilities`)

Набор правил один для всех режимов, но проверять можно только то, что разбор
действительно измерил. `ParsedDocxDocument.capabilities` — матрица
возможностей: `styles_parsed` истинно для DOCX (есть `styles.xml`, `w:pPr`,
`numbering.xml`) и ложно для `pdf_only`, где документ восстановлен по геометрии
листов.

| Правило | `docx_only` / `docx_pdf` | `pdf_only` (`styles_parsed=false`) |
|---|---|---|
| `font` — гарнитура | сверяется | сверяется по нормализованному имени: запись шрифта PDF (`TimesNewRoman`, `ABCDEF+…`) не шумит, другая гарнитура (`LiberationSans`, `NimbusRomNo9L`, `CMR10`) — нарушение |
| `font` — `font_cs` | сверяется при `check_complex_script` | **не проверяется**: complex script в PDF не измеряется |
| `font` — кегль, начертание | сверяется | сверяется: кегль и флаги шрифта измерены по спанам |
| `indent` | сверяется по `w:pPr` | **не проверяется**: источник требования ненадежен (артефакты списков дают ложные +20 мм) |
| `margin` | допуск `tolerance_mm` | допуск `max(tolerance_mm, 1.5)` мм: поля оценены по геометрии |
| `heading_*`, `required_sections`, `toc` | по `document_tree` / `TocContainerBlock` | так же: структура восстановлена PDF-парсером |

Смысл деградации — не скрыть нарушение, а не выдумать его из отсутствующего
измерения. Поэтому в `pdf_only` `indent` не создает нарушений и не увеличивает
`summary.objects_checked` (его источник — геометрия, а не `w:pPr`), `font_cs` не
сверяется, а `font` продолжает ловить настоящую другую гарнитуру
(`LiberationSans`) и неверный кегль (12 pt вместо 14 pt). Поле 13.7 мм при
ожидаемых 15 мм (отклонение 1.3 мм) в допуск ±1.5 мм укладывается, поэтому
нарушением не является: 1.5 мм — погрешность оценки геометрии, а не разрешенное
отклонение; нарушением остается расхождение больше допуска (например, нижнее
поле 26.5 мм при ожидаемых 20 мм).

В `pdf_only` парсер измеряет красную строку как сдвиг первой строки абзаца
относительно второй (`parse_pdf` → `ParagraphPropertiesEffective`). Если строка
одна, абзац — заголовок/список, выключен по центру или сдвиг неправдоподобно
велик (колонки, склейка строк), значение равно `None`
(`indent_first_line_source="pdf_unmeasured"`), а не `0`: «не измерено» и
«отступа нет» — разные факты. Поэтому `indent` в `pdf_only` не проверяется: сам
измеритель честный, но источник требования — верстка PDF, а не `w:pPr`, и
артефакты разметки (маркеры списков, колонки) дают ложные +20 мм.

### `heading_levels` — иерархия заголовков

| Поле | По умолчанию | Смысл |
|---|---|---|
| `first_level` | `1` | уровень, с которого начинается документ |
| `allow_skipped_levels` | `false` | разрешить переход `1 → 3` без промежуточного уровня |
| `max_level` | `null` | максимальная глубина вложенности заголовков |

Уровни берутся из `document_tree` (узел `level`), то есть парсер уже свел
`outlineLvl`, стили заголовков и глубину номера. Для нумерованного заголовка
уровень равен глубине номера: `3.1.1` — третий уровень, и при расхождении с
`outlineLvl` или стилем абзаца побеждает номер. Это калибровка по корпусу: в ВКР
УрФУ стили «Пункт»/«Подпункт» объявляют `outlineLvl` на единицу глубже
нумерации, поэтому «3.1.1 Блок…» получал уровень 4–5, правило видело перескок, а
роль раздела становилась `sub_section` вместо `main_chapter` у главы. Стиль
по-прежнему задает уровень заголовка без номера. Нарушение сообщает пару
«ожидаемый уровень → фактический»: `first_level`, `max_level` или
`max_level_after_previous`.

### `heading_numbering` — нумерация разделов

| Поле | По умолчанию | Смысл |
|---|---|---|
| `check_sequence` | `true` | номера соседних заголовков идут подряд: 1, 2, 3 |
| `check_parent_number` | `true` | номер подраздела начинается с номера родителя: `1.2` внутри `1` |
| `check_depth_matches_level` | `true` | глубина номера соответствует месту в иерархии: у потомка на единицу больше, чем у ближайшего пронумерованного предка |
| `number_ending` | `any` | `with_dot` / `without_dot` — требование к точке после номера |
| `require_number_for_roles` | `["main_chapter", "sub_section"]` | роли, которые обязаны быть пронумерованы |

Последовательность считается внутри групп соседних заголовков (сиблингов) и
отдельно по глубине номера, поэтому перезапуск нумерации в приложениях не ломает
проверку разделов. Номера, которые не разбираются как `1.2.3` (например
`Приложение А`), в последовательности не участвуют, но проверяются на
обязательность по роли. В нарушении видно, какой номер ожидался и какой найден.

`check_depth_matches_level` сравнивает глубину номера не с уровнем заголовка
(уровень нумерованного заголовка вычислен из этой же глубины, и проверка стала бы
тавтологией), а с местом номера в иерархии: ожидаемая глубина — на единицу
больше, чем у ближайшего пронумерованного предка. Так «3.1.1» внутри «3.1»
корректен, а «3.1.1» сразу после главы «1» — нарушение. У номера верхнего уровня
(заголовок без родителя) ожидание не определено: стартовый уровень проверяет
`heading_levels`, чтобы одно нарушение не приходило от двух правил.

`require_number_for_roles` задает, какие роли проверять, но не отменяет
структуру работы: роли из `NUMBERLESS_HEADING_ROLES` (`bibliography`,
`introduction`, `conclusion`, `appendix`, `title_page`, `task_sheet`,
`abbreviations`) номер не требуют, даже если перечислены в этом списке.
Нумеруются главы (`main_chapter`) и подразделы (`sub_section`).


### `heading_format` — оформление заголовка

| Поле | По умолчанию | Смысл |
|---|---|---|
| `trailing_dot` | `any` | `forbid` / `require` — точка в конце текста заголовка |
| `trailing_dot_in_number` | `any` | точка после номера (`1.` в начале строки) |
| `case` | `any` | `uppercase`, `capitalized`, `not_uppercase` |
| `alignment` | `null` | ожидаемое `effective_props.alignment`: `left`, `center`, `right`, `both`, `distribute` |

Регистр проверяется по буквам заголовка: `capitalized` требует прописную первую
букву и запрещает заголовок целиком прописными, `uppercase` — наоборот.
Несколько расхождений одного заголовка собираются в одно нарушение, чтобы
нормоконтролер видел заголовок, а не три записи подряд.

### `required_sections` — состав и порядок разделов

Разделы задаются списком `sections`; каждый элемент — `label` (метка для отчета
и `violation_id`), `role` (семантическая роль из `document_tree`), `titles`
(допустимые названия) и `required`. Метки уникальны.

```json
{
  "label": "заключение",
  "role": "conclusion",
  "titles": ["ЗАКЛЮЧЕНИЕ"],
  "required": true
}
```

`titles` сравниваются без учета регистра, точки, двоеточия и лишних пробелов и
допускают продолжение названия: `СПИСОК ЛИТЕРАТУРЫ` совпадет с
`СПИСОК ЛИТЕРАТУРЫ ПО ТЕМЕ`. Это же поле отделяет структурное `ЗАКЛЮЧЕНИЕ` от
главы `ВЫВОДЫ`, у которой та же роль `conclusion`. Пропуск раздела дает
нарушение уровня документа (`<rule_id>:section:<label>`), а раздел, оказавшийся
выше предыдущего, — нарушение на своем заголовке.

Список литературы в разных ВКР называется по-разному, поэтому для него задана
группа синонимов (`SECTION_TITLE_SYNONYMS` в `engine.py`): `СПИСОК ЛИТЕРАТУРЫ`,
`СПИСОК ИСПОЛЬЗОВАННОЙ ЛИТЕРАТУРЫ`, `СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ`,
`СПИСОК ИСПОЛЬЗУЕМЫХ ИСТОЧНИКОВ`, `СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ И
ЛИТЕРАТУРЫ`, `СПИСОК ИСТОЧНИКОВ`, `БИБЛИОГРАФИЧЕСКИЙ СПИСОК`, `БИБЛИОГРАФИЯ`,
`ИСТОЧНИКИ`, `ЛИТЕРАТУРА`. Любое из них закрывает требование
`{"label": "список литературы", "titles": ["СПИСОК ЛИТЕРАТУРЫ"]}`, в том числе с
уточнением в начале: `СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ ПО ТЕМЕ РАБОТЫ`.
Подзаголовок «Обзор использованных источников» синонимом не считается: он не
начинается с названия раздела.

### Служебные метки и роли заголовков

Разбор присваивает строке заголовок только тогда, когда она называет элемент
структуры работы. Метки служебных страниц — `ВЫПУСКНАЯ КВАЛИФИКАЦИОННАЯ РАБОТА`,
`РАБОТА ВЫПОЛНЕНА` и `ЗАДАНИЕ` (`ЗАДАНИЕ НА ВКР`, `ЗАДАНИЕ НА ВЫПУСКНУЮ
КВАЛИФИКАЦИОННУЮ РАБОТУ`, `ЗАДАНИЕ НА ДИПЛОМНОЕ ПРОЕКТИРОВАНИЕ`) — заголовками
не считаются ни в DOCX, ни в PDF (`parser/core/heading_labels.py`). В DOCX они
часто набраны стилем Heading1, а в PDF крупный полужирный кегль — единственный
признак заголовка, поэтому без этого правила титул давал ложный первый раздел
второго уровня, требование номера и запись в оглавлении. Обычный заголовок со
словом «задание» («ЗАДАНИЕ НА ПРОЕКТИРОВАНИЕ АСУ», «Техническое задание, лист
1») заголовком остается.

Роли разделов определяются по началу названия, и у списка литературы, перечня
сокращений и приложений есть синонимы:

| Роль | Названия (начало строки) |
|---|---|
| `bibliography` | `СПИСОК ЛИТЕРАТУРЫ`, `СПИСОК ИСТОЧНИКОВ`, `СПИСОК ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ`, `БИБЛИОГРАФИЧЕСКИЙ СПИСОК`, `БИБЛИОГРАФИЯ`, `ИСТОЧНИКИ` |
| `abbreviations` | `СПИСОК СОКРАЩЕНИЙ`, `ПЕРЕЧЕНЬ СОКРАЩЕНИЙ`, `СПИСОК ТЕРМИНОВ`, `ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ`, `ГЛОССАРИЙ` |
| `appendix` | `ПРИЛОЖЕНИЕ А`, `ПРОДОЛЖЕНИЕ ПРИЛОЖЕНИЯ А`, `ОКОНЧАНИЕ ПРИЛОЖЕНИЯ Б` |

Вхождения ключевых слов в середину названия роль не назначают: «Обзор
использованных источников» — подраздел главы, а не список литературы. Строка,
начинающаяся со строчной буквы («определения потенциальных путей…»,
«литература, ГОСТы»), заголовком не становится даже при совпадении первого
слова: это обычный текст или реквизит листа задания.

### `toc` — оглавление

| Поле | По умолчанию | Смысл |
|---|---|---|
| `require_toc` | `true` | требовать наличие оглавления |
| `require_automated` | `false` | требовать поле `TOC`/SDT вместо ручного списка |
| `require_page_numbers` | `true` | номер страницы в каждой записи |
| `check_page_numbers` | `false` | сверять номер страницы с фактической страницей заголовка |
| `check_titles` | `true` | сверять названия записей с найденными заголовками |
| `require_dot_leader` | `false` | требовать отточие до номера страницы |
| `check_completeness` | `null` | требовать присутствия разделов из `required_entries`; по умолчанию включается, если `required_entries` задан |
| `required_entries` | `[]` | список разделов в формате `SectionSpec` (как у `required_sections`) |
| `max_depth` | `null` | до какой глубины заголовки обязаны быть в оглавлении: `2` — главы и разделы, `null` — все уровни |

`check_page_numbers` включается только вместе с точной пагинацией (PDF): при
оценочной разметке парсер оставляет `is_page_number_match = None`, и правило
молча ничего не сверяет. `check_completeness` без `required_entries` — ошибка
загрузки набора, потому что сверять полноту не с чем. `max_depth` без
`check_completeness` — тоже ошибка: поле задает глубину сверки полноты, а не
оформление записей.

`max_depth` — калибровка по корпусу ВКР: оглавление содержит главы и разделы, но
почти никогда не перечисляет подразделы третьего уровня (`3.1.1`). При
`max_depth: 2` такой подраздел пропуском не считается, а пропуск главы остается
нарушением: уровень главы всегда попадает в сверяемую глубину. Записи глубже
`max_depth` в оглавлении допускаются — это оформление оглавления, а не
нарушение (уровень записи в стиле `TOC3` — не ошибка).

**Миграция наборов.** `max_depth` теперь задает глубину сверки полноты, а не
максимальный уровень записи. Набор, в котором задан `max_depth`, но нет
`check_completeness: true` (и `required_entries`), не загрузится: движок
сообщит об ошибке конфигурации. Прежнее поведение «не глубже N» отдельным полем
не заменяется — уровень записи больше не ограничивается, потому что это
оформление оглавления. Наборы без `max_depth` работают как раньше.

### Сверка записей оглавления с приложениями

Запись `ПРИЛОЖЕНИЕ А` указывает на приложение, а не на заголовок с таким
текстом, поэтому правило доводит сопоставление, которое разбор сделал по
названию:

* приложение ищется по букве среди заголовков приложений, подписей
  «Продолжение ПРИЛОЖЕНИЯ А»/«Окончание приложения Б» и сущностей
  `entity_type="appendix"` из `cross_ref_index`;
* если буквы в тексте нет (титул приложения набран как «(обязательное) Название»
  без «ПРИЛОЖЕНИЕ А»), приложение ищется по названию: подпись отвечает записи
  «ПРИЛОЖЕНИЕ А (обязательное) Название»;
* одна запись приложения покрывает и подзаголовки внутри него: «ПРИЛОЖЕНИЕ А
  (обязательное) Матрица ответственности» закрывает требование к заголовку
  «Матрица ответственности», поэтому подраздел приложения не выглядит забытым
  в оглавлении.

Записи, которые разбор не сопоставил из-за отточия (PDF отдает «1.2 Сбор и
анализ требований……» с отточием), сопоставляются по номеру и названию: если
номер записи совпадает с номером заголовка, а название заголовка входит в
запись, заголовок считается указанным в оглавлении.

### `page_number_position` — положение номера страницы

| Поле | По умолчанию | Смысл |
|---|---|---|
| `zone` | обязательно | `header` — номер в верхнем колонтитуле, `footer` — в нижнем |
| `alignment` | `center` | ожидаемое выравнивание абзаца с номером |

Профили вузов задают положение парой «колонтитул + выравнивание»: `top_center`
из PDF-методички — это `{"zone": "header", "alignment": "center"}`, а
`bottom_center` — `{"zone": "footer", "alignment": "center"}`. Названия
`top_center`/`bottom_center` схемой не принимаются: в DOCX номер лежит не в
геометрии листа, а в конкретном колонтитуле. `zone` обязателен — без него
правило ничего не проверяет.

Движок берет положение из `pdf_pages_audit` (поля `page_number_location` и
`page_number_alignment`): считается мода пар «зона + выравнивание», и она
сравнивается с ожиданием. Чтобы не выдумывать вердикт по двум-трем случайным
номерам, проверка включается только при `number_count >= max(3, N // 3)`, где
`N` — число страниц PDF (порог перенесен из `pdf_norm_control_parser`); иначе
правило получает `not_assessed` с причиной. Для DOCX без PDF источником служат
колонтитулы секций (`has_page_field`/`has_hardcoded_number` и
`page_number_alignment`); если номера нет вовсе, проверка тоже `not_assessed`.

### `page_format` — формат листа

| Поле | По умолчанию | Смысл |
|---|---|---|
| `width_mm` | `210.0` | ширина листа, мм |
| `height_mm` | `297.0` | высота листа, мм |
| `tolerance_mm` | `1.0` | допуск к каждой стороне, мм |
| `orientation` | `portrait` | `portrait`, `landscape`, `any` |

По умолчанию правило описывает A4 (210 × 297 мм) с допуском ±1 мм. Размеры
обязаны согласовываться с ориентацией: для `portrait` ширина меньше высоты,
для `landscape` — больше; `any` снимает это ограничение. Формат проверяется по
каждой секции, как и `margin`: альбомная вставка внутри документа дает
нарушение на своей секции, а не на всем файле.

Сравнение числовое: каждая сторона сверяется с `width_mm`/`height_mm` с допуском
`tolerance_mm`, ориентация — с полем `orientation` секции. Флаг парсера
`is_a4_standard` в вердикт не входит: у него собственный допуск ±2 мм, шире
правила, поэтому он приводится только в `found` как контекст. Если секций нет,
правило получает `not_assessed`, а не считается выполненным.

### `line_spacing` — межстрочный интервал

| Поле | По умолчанию | Смысл |
|---|---|---|
| `ratio` | `1.5` | множитель интервала: `1.5` — полуторный, `1.0` — одинарный |
| `tolerance` | `0.25` | допуск по множителю |

Интервал задается множителем, а не пунктами: `1.5` соответствует
`w:spacing w:line="360" w:lineRule="auto"` при кегле 14 pt. Допуск задан в тех
же единицах, что и множитель, поэтому профили вузов берут ±0.25 — это ровно
половина шага между одинарным и полуторным интервалом.

Источник зависит от режима разбора. В DOCX берутся абзацы основного текста
(та же выборка, что у `font`/`indent`: без заголовков и подписей) с
множительным интервалом `lineRule="auto"`; медиана их `line_spacing_value`
сравнивается с `ratio`. Абзацы с `exact`/`atLeast` в множитель не переводятся и
в выборку не попадают: значение в пунктах несравнимо с множителем.

В `pdf_only` измеряется типографское отношение `шаг / кегль` (медиана по парам
соседних строк). Это не множитель Word: одиночная строка Word занимает около
1,15 кегля, поэтому измеренное отношение систематически больше множителя.
Замеры на Word-PDF в Times New Roman:

| Множитель Word | Типографское `шаг / кегль` |
|---|---|
| 1,0 | ≈1,15 |
| 1,1 | ≈1,27 |
| 1,3 | ≈1,49 |
| 1,5 | ≈1,72 |
| 1,6 | ≈1,84 |
| 1,75 | ≈2,01 |

Поэтому перед сравнением измеренное значение делится на
`PDF_SINGLE_LINE_FACTOR = 1.15` — одиночный интервал Times New Roman. После
этого `expected.ratio` имеет единый смысл в обоих режимах: множитель Word
`1.5 ± 0.25`. В `details` и `found` сохраняются оба значения: `median_ratio` —
исходное типографское отношение, `word_multiplier` — приведенное к шкале Word;
сам коэффициент отдается как `pdf_single_line_factor`. Вердикты DOCX и PDF для
одного и того же множителя совпадают: 1,6 в обоих режимах проходит допуск,
1,1 — нет.

Коэффициент зависит от гарнитуры: у Arial одиночная строка занимает около
1,2 кегля, поэтому на документах не в Times New Roman конверсия смещается
примерно на 4 %. Это осознанное ограничение одного коэффициента: профили вузов
требуют Times New Roman, и для проверяемого шрифта погрешность минимальна.

Порядок источников `pdf_only`: `meta.pdf_median_leading_ratio`, затем медиана
постраничных `pdf_pages_audit[].leading_ratio`, иначе `not_assessed`. Если
пригодных данных нет, правило получает `not_assessed`, а не ложный `pass`.

Абзацы PDF-структуры (`line_spacing_source == "pdf_estimate"`) в выборку не
попадают: их значение — не множитель Word и не типографское отношение, а оценка
структуры PDF вида `шаг / (кегль × 1,2)`, привязанная к делению строки в этом
слое. Смешивать её с `meta.pdf_median_leading_ratio` нельзя: медиана уезжает к
1,25, и полуторный интервал проходит только по допуску.

Что важно знать про отчет:

- `expected`/`found` — машинно-читаемые значения только по тем полям, которые
  правило проверяло и которые не совпали. Ими удобно пользоваться в тестах и в
  интерфейсе.
- `expected_text`/`found_text` — те же значения словами, для выгрузки
  нормоконтролеру.
- Нарушение адресуется **абзацем**, а не раном: `occurrences` показывает,
  сколько ранов внутри абзаца не соответствует правилу. Для `margin` адрес —
  секция (`violation_id = "<rule_id>:section:<idx>"`), для `required_sections` —
  раздел (`"<rule_id>:section:<label>"`), для `toc` — запись
  (`"<rule_id>:toc:<toc_id>:entry<N>"`) или заголовок, забытый в оглавлении
  (`"<rule_id>:toc:missing:<block_id>"`).
- `passed` равен `true`, только если нет нарушений уровня `error`. Правила с
  `severity="warning"` или `"info"` не блокируют документ.
- `assessments` — статусы проверок, которым может не хватить данных: `status`
  равен `pass`, `fail` или `not_assessed`, а `confidence` — `high`, `medium` или
  `low`. `fail` всегда дублируется нарушением в `violations`, `pass` и
  `not_assessed` нарушений не создают. Свойство `report.not_assessed` возвращает
  только неоцененные проверки, `summary.not_assessed_total` — их число.
- `confidence` у нарушения показывает надежность проверки: `high` — точные
  данные DOCX, `medium` — оценка по PDF, `low` — данных почти нет (бывает у
  `not_assessed`).
- Отчет детерминирован: нет таймстемпов и абсолютных путей, поэтому два прогона
  на одном файле дают одинаковый JSON. Это позволяет сравнивать отчеты
  «до/после» правок.

## 5. Что проверяется не всегда

Сознательные ограничения первой итерации:

1. **Шрифт абзацного знака** (`para_mark_font_effective`) не проверяется —
   нарушение ищется по видимому тексту.
2. **Complex script** (`font_cs`) по умолчанию выключен: в русских документах он
   часто заполняется шумом. Включается флагом `check_complex_script`.
3. **Поля и отступы** сравниваются с абсолютным значением допуска; специальных
   правил для «допустимого диапазона» нет. Единственное исключение — поля в
   `pdf_only`: там допуск расширяется до ±1.5 мм, потому что поля измерены по
   геометрии текста.
4. **Гарнитура** сравнивается по нормализованному имени (`TimesNewRoman` ==
   `Times New Roman`, subset-префикс и стилевые маркеры отбрасываются); алиасы
   вроде `Times New Roman CYR` попадут в нарушения — это осознанно. В `pdf_only`
   гарнитура сверяется так же, а `font_cs` — нет (complex script в PDF не
   измеряется).
5. **Стили не анализируются как цепочка**: проверяется результат каскада, а не
   то, в каком стиле задано значение. Для отладки в `found` отступа добавляется
   `first_line_source` (`direct`, `paragraph_style`, `doc_defaults` и т.п.).
6. **Строки оглавления** не попадают в текстовые правила: их проверяет
   отдельный `toc`, а `font`/`indent` со `scope="body_text"` их не видят.
7. **Уровни и роли заголовков берет парсер**: если заголовок распознан
   эвристически, структурные правила работают по этой оценке. Сузить выборку
   можно через `min_heading_confidence`, а приложения и задание исключить через
   `exclude_roles`.
8. **Номера страниц в оглавлении** сверяются только при точной пагинации из
   PDF (`check_page_numbers`): при оценочной разметке парсер не выставляет
   `is_page_number_match`, и правило не выдумывает расхождения.
9. **Приложения** часто перезапускают нумерацию разделов, поэтому в штатном
   наборе структурные правила исключают роль `appendix`; проверка самих
   приложений — отдельная задача.
10. **Титульный лист и листинги** по умолчанию не проверяются текстовыми
    правилами (`exclude_contexts`): их оформление задано отдельными разделами
    методички. Вернуть проверку можно через `"exclude_contexts": []` или убрать
    из списка нужный контекст.
11. **Классификатор контекста консервативен**: блок без уверенных признаков
    остается `body`. Поэтому титульный лист без реквизитов или листинг в
    пропорциональной гарнитуре без код-синтаксиса проверяются как обычный текст.
12. **Номер страницы** проверяется по данным PDF-аудита
    (`pdf_pages_audit`: зона и выравнивание) и только при достаточном числе
    распознанных номеров; PDF-положения `top_center` и `bottom_center`
    переводятся в пару «колонтитул + выравнивание». Без PDF источником служат
    поля колонтитулов DOCX, а при отсутствии данных правило получает
    `not_assessed`. Геометрия полосы номера (30 мм у края, 25 мм от центра)
    остается в PDF-парсере.
13. **Межстрочный интервал** сравнивается по множителю Word: в DOCX — по
    `w:spacing` абзацев с `lineRule="auto"`, в `pdf_only` — по типографскому
    отношению `шаг / кегль`, приведенному к множителю делением на
    `PDF_SINGLE_LINE_FACTOR = 1,15`. Оценка абзацев PDF-структуры
    (шаг / (кегль × 1,2)) — другая величина, в проверку она не попадает. Точный
    интервал в пунктах (`exact`) и «не менее» (`atLeast`) в множитель не
    переводятся: такие абзацы в выборку не входят, а при отсутствии других
    данных правило получает `not_assessed`.

## 6. Как добавить правило

1. Возьмите существующий пример из `rule_engine/rules/vkr_test_rules.json`.
2. Задайте `rule_id`, `kind`, `message` и `target.scope`.
3. Заполните `expected` только теми полями, которые действительно требует
   методичка: незаполненные поля не проверяются.
4. Прогоните документ и посмотрите сводку:

```bash
python manual_test/check_rules.py manual_test/test.docx --rules my_rules.json --limit 20
```

5. Если правило ловит лишнее, сначала настройте `target`
   (`include_headings`, `style_ids`, `exclude_roles`, `exclude_contexts`,
   `min_heading_confidence`), и только потом трогайте `tolerance`.
6. Проверьте набор в тестах: `RuleSet.model_validate(json.loads(...))` падает на
   противоречивых правилах, поэтому ошибку видно без запуска документа.

Пример правила для подписей рисунков:

```json
{
  "rule_id": "font_captions",
  "kind": "font",
  "severity": "warning",
  "message": "Подписи рисунков набираются 12 pt",
  "target": {"scope": "body_text", "include_captions": true},
  "expected": {"size_pt": 12.0, "size_tolerance_pt": 0.5}
}
```

## 7. Ограничения и направление развития

Чего в наборе пока нет:

- выравнивания основного текста, отступов списков, интервалов до и после
  абзаца (сам межстрочный интервал уже проверяется правилом `line_spacing`);
- нумерации страниц сверх положения номера: пропуск номера на титульном листе,
  отдельная нумерация приложений и формат `Страница 5 из 80` не описаны;
- проверки самих приложений: их нумерация и оформление пока исключены из
  структурных правил;
- автоматического подбора требований по методичке — набор пишется руками;
- отчета для человека в Markdown/PDF: есть JSON и консольная сводка.

Задел на следующие шаги:

- новые `kind` (`alignment`, `paragraph_spacing`) добавляются как
  дискриминированные модели в `rules.py` и отдельный метод проверки в
  `engine.py`; остальной код не меняется;
- структурные правила переиспользуют `SectionSpec`, поэтому новые проверки
  («аннотация», «перечень сокращений», «приложения») описываются данными без
  правки движка;
- если понадобится «допустимый диапазон», в `expected` можно добавить
  `min_mm`/`max_mm` без ломания существующих наборов;
- `check_json_file()` позволяет прогонять правила на уже собранных JSON без
  повторного разбора и без LibreOffice.

## 8. Тесты

```bash
python -m pytest tests/test_rule_schema.py tests/test_rules_engine.py tests/test_rule_engine_page_layout.py \
    tests/test_rules_fonts.py tests/test_rules_indents.py tests/test_rules_margins.py \
    tests/test_rules_headings.py tests/test_rules_sections.py tests/test_rules_toc.py \
    tests/test_heading_calibration.py tests/test_toc_matching.py -q
python -m pytest tests -q
```

Сверку оглавления с приложениями и глубину проверки полноты закрепляет
`tests/test_toc_matching.py`: запись «ПРИЛОЖЕНИЕ А» находит приложение по букве
(заголовок или «Продолжение ПРИЛОЖЕНИЯ Б»), титул приложения без буквы
сопоставляется по названию, одна запись приложения покрывает свои подзаголовки,
`max_depth: 2` не считает пропуском подраздел «1.1.1», пропуск главы остается
нарушением, а запись глубже `max_depth` — не нарушение.

Калибровку заголовков закрепляет `tests/test_heading_calibration.py`: уровень
нумерованного заголовка равен глубине номера (`3.1.1` → 3 при `outlineLvl` 4–5,
автонумерация `%1.%2.%3` и стиль с цифрой в имени), «1.1.1» сразу после главы
«1» по-прежнему нарушение глубины, титульные метки не становятся заголовками ни
в DOCX, ни в PDF (и не дают нарушений уровней и оглавления), синонимы списка
литературы закрывают требование `required_sections`, а структурные роли не
требуют номера; выравнивание «по ширине» правило оформления продолжает ловить.

Обратная совместимость наборов и детерминизм отчета закреплены отдельно:
`tests/test_rules_context_compat.py` загружает JSON без `exclude_contexts`, с
валидным и с некорректным значением поля, а также сверяет два прогона одного
документа побайтово. Сервисные зоны проверяют `tests/test_rule_context.py`
(титул УРФУ на третьей странице, акт внедрения в середине документа, реквизиты
«Екатеринбург»/«2026»/«(фамилия, имя, отчество)», возврат зоны в основной текст),
`tests/test_rules_context_filter.py` (строки акта не дают нарушений шрифта и
отступа, а абзац с упоминанием подписи продолжает проверяться) и
`tests/test_rule_context_integration.py` (DOCX с листом задания на двух страницах
и титулом на третьей).

Деградацию по `capabilities` и честное измерение отступа в PDF закрепляет
`tests/test_pdf_only_rules.py`: синтетический PDF через PyMuPDF (отступ 12.5 мм,
абзац без отступа, одиночная строка, заголовок) проверяет, что `parser.pdf`
измеряет красную строку сдвигом первой строки относительно второй и отдает
`None` там, где измерить нельзя; что в `pdf_only` правило отступов не создает
нарушений, гарнитура сверяется по нормализованному имени (`TimesNewRoman` ==
`Times New Roman` — не нарушение, `Arial` — нарушение), `font_cs` не сверяется,
кегль продолжает сверяться, а допуск полей страницы — ±1.5 мм (отклонение
1.5 мм проходит; поле 13.7 мм при ожидаемых 15 мм отклоняется на 1.3 мм и
нарушением не является, а расхождение больше 1.5 мм — является). Те же
проверки на DOCX подтверждают, что строгий режим не изменился.

Совместимость с готовыми JSON-отчетами закрепляет
`tests/test_legacy_json_schema.py`: отчеты схемы 3.0.0 всех трех режимов
(`docx_only`, `pdf_only`, `docx_pdf`) валидируются текущей `ParsedDocument` и
прогоняются правилами без повторного разбора. Числа шума корпуса и служебные
зоны закрепляет `tests/test_corpus_noise_regression.py` (корпус `manual_test`
gitignored, поэтому корпусные тесты пропускаются при его отсутствии).

Тесты собирают DOCX из XML-фрагментов (`DocxPackageBuilder`), поэтому не
зависят от бинарных образцов и проверяют именно тот контракт, который нужен
правилам: разрешенный каскад стилей, исключения по `scope` и точность адреса
нарушения. Схема новых видов правил и загрузка профилей проверяются там же —
в `tests/test_rule_schema.py`. Проверки номера страницы, формата листа и
межстрочного интервала работают на синтетических `ParsedDocument` без реальных
PDF: `tests/test_rule_engine_page_layout.py` покрывает `pass`, `fail` и
`not_assessed` для всех трех видов.

## 9. Профили вузов

Готовые наборы лежат рядом со штатным: `rule_engine/rules/mpgu.json`,
`urgpu.json`, `urfu.json`. Набор по умолчанию (`vkr_test_rules.json`) не
меняется, поэтому профили можно подключать постепенно. Загрузка по id вуза:

```python
from rule_engine.rules import available_profiles, load_profile_ruleset

available_profiles()            # ('mpgu', 'urgpu', 'urfu')
ruleset = load_profile_ruleset("urgpu")
```

Идентификатор сравнивается без учета регистра и пробелов по краям; неизвестный
профиль — `ValueError`, а не тихий переход к набору по умолчанию.

| Профиль | Поля (л/п/в/н), мм | Номер страницы | Формат листа |
|---|---|---|---|
| `mpgu` | 30 / 15 / 20 / 20 | верхний колонтитул, по центру | не проверяется |
| `urgpu` | 30 / 20 / 25 / 25 | нижний колонтитул, по центру | не проверяется |
| `urfu` | 30 / 15 / 20 / 20 | нижний колонтитул, по центру | A4 210 × 297 мм, ±1 мм |

Общие требования во всех профилях одинаковы: Times New Roman 14 pt (±0.5),
отступ первой строки 12,5 мм (±2.5), полуторный интервал 1.5 (±0.25), поля с
допуском 3 мм — допуск шире, чем у штатного набора, потому что профиль
перенесен из PDF-методички, где поля оцениваются по границам текста.

Пример профильного правила:

```json
{
  "rule_id": "page_number_position",
  "kind": "page_number_position",
  "severity": "warning",
  "message": "Номер страницы печатается в нижнем колонтитуле по центру",
  "requirement_ref": "Методические указания УрФУ, требования к нумерации страниц",
  "target": {"scope": "headers_footers"},
  "expected": {"zone": "footer", "alignment": "center"}
}
```

`severity="warning"` у положения номера: требование обязательное, но
распознавание колонтитула зависит от того, как документ собран, поэтому
нарушение не блокирует работу (см. `passed` в отчете). Остальные правила
профиля — `error`.

Свой профиль добавляется без правки схемы правил: положите `<id>.json` рядом и
допишите пару `"<id>": Path(...)` в `PROFILE_RULESET_PATHS` (`rules.py`).
